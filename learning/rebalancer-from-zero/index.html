Meta's open-source Rebalancer

Who sits where? How Meta places millions of jobs on millions of computers.

You do not need to know anything about servers or infrastructure. We start with a wedding seating chart and build up from there. Every technical word gets explained the first time it shows up.

1. The idea

It is a seating chart

You are planning a wedding. You have guests. You have tables. Your job is to decide which guest sits at which table. Every guest gets exactly one seat.

Rebalancer solves this kind of puzzle. The textbook name is an assignment problem: a pile of things, a set of places, and a decision about which thing goes where.

Now swap the words. At Meta the "guests" are programs and pieces of data. The "tables" are the physical computers (servers) in data centers. Here is the translation:

Everything else in Rebalancer builds on these five ideas: objects, containers, dimensions, scopes, partitions.

2. Why it is hard

Too many possible seating charts

With 3 guests and 2 tables you can check every option by hand. Each guest has as many choices as there are tables, so the total is tables multiplied by itself once per guest. Try the sliders.

95 trillion
possible seating charts

Assumes a computer that checks one billion seating charts every second, which is very fast.

Meta has millions of servers, so the real count has millions of digits. Checking all of it is not an option. Computer scientists call problems like this NP-hard: nobody knows a trick that always avoids searching an enormous number of options.

So Rebalancer does not check everything. It has two different strategies for finding a good answer without trying every option. Before those, you need to know what "good" means.

3. Rules and wishes

What makes a seating chart good

You describe "good" to Rebalancer in two kinds of statements.

Rules · constraints

Must be true

  • A table cannot hold more than 4 people.
    For servers: a computer cannot use more memory than it has. CapacitySpec
  • Table C is being cleaned. Keep it empty.
    For servers: a machine going down for maintenance must hold nothing. ToFreeSpec
  • Never seat two members of one family at the same table.
    For servers: two copies of a program must not share a rack, so one power failure cannot kill both. GroupCountSpec
Wishes · goals

Make as good as possible

  • Keep the tables about equally full.
    For servers: no machine should be overloaded while others sit idle. BalanceSpec
  • Move as few people as possible from where they sit now.
    For servers: moving a program costs time and risk. MinimizeMovementSpec

Rebalancer ships these as ready-made templates called specs (short for specifications). You fill in a form, such as "which number to measure" and "which group of containers". You do not write the math yourself. The grey names above are the real spec names in the code.

One more detail. If the starting layout already breaks a rule, Rebalancer does not give up. It treats "fix the broken rule" as a very high priority wish, and it never lets that rule get worse while fixing it.

4. Strategy one

Local search: fix the worst table, repeat

This is the default strategy, and the one Meta uses for its biggest problems. The plan is simple:

Look at the current seating. Find the most overcrowded table. Try moving each person from it to every other table. Do the single move that helps the most. Repeat.

"Local" means it only ever looks at small changes near the current layout. Below is a working copy of that loop. There are 12 tasks (the blue squares) and 4 hosts (servers). What the algorithm is thinking

    Simplified on purpose: this demo has one kind of move (move a single task) and one wish (even out fullness). The real thing has dozens of move types and more than 25 kinds of rules and wishes. The score here is the sum of squared gaps from the average, a cousin of Rebalancer's real balance formulas.

    The recipe, in plain steps

    1. 1

      Score the current layout

      One number that says how far the layout is from ideal. Lower is better.

    2. 2

      Rank hosts from hottest to coldest

      "Hot" means a host that adds the most to the bad score, such as the most overloaded one. In the code this job belongs to a piece called HotContainerSelector.

    3. 3

      Take the hottest host and try moves out of it

      Every task on it, to every other host. Each kind of small change is called a move type. "Move one task" is the simplest. "Swap two tasks" is another. You choose which ones Rebalancer may use.

    4. 4

      Check each move against the rules, then keep the best

      A move is thrown out if it breaks a rule, makes a higher-priority wish worse, or does not improve the score. Rebalancer only accepts strictly better moves.

    5. 5

      Applied a move? Re-rank and go again. No move helped? Skip this host for now.

      After a successful move the ranking changes, so Rebalancer re-ranks. A host with no useful move gets set aside until the next pass.

      loop back to step 2
    6. 6

      Stop

      When no host can be improved, when the score reaches the best value mathematically possible, or when a time or move limit runs out.

    The real loop lives in CoreLocalSearchSolve.cpp, in a function called solve(). It is about 90 lines and follows these six steps closely.

    5. Where it gets stuck

    The hiker in the fog

    Local search is like a hiker in thick fog who always walks downhill, because lower ground means a better score. It reaches the bottom of a valley and stops: every direction from there goes up. The hiker cannot see that a much deeper valley exists further away.

    The stuck spot is called a local optimum: the best layout reachable by small changes, but not necessarily the best layout that exists. The score at the very bottom of the deepest valley is the global optimum.

    Rebalancer's own Eight Queens example shows this. The puzzle is to place 8 chess queens so none attack each other. Run with simple one-queen moves, the local search gets stuck. A comment in the example's code explains why: none of the simple individual moves can take the board to a perfect solution. The example offers a --optimal option that switches to the second strategy, which solves it.

    Two ways to reduce the problem: give the search more kinds of moves (swap two, rotate three), or switch strategies.

    6. Strategy two

    The math engine (the "MIP solver")

    The other strategy turns your seating problem into equations and hands them to a specialist program. The acronym is MIP, short for Mixed-Integer Programming. That is a branch of math for problems where some quantities must be whole numbers, such as yes or no, because a guest cannot sit half at a table.

    Here is how it works, in four moves:

    1. 1

      Give every guest-and-table pair a switch

      1 means "this guest sits at this table". 0 means "no".

    2. 2

      Write the rules as arithmetic on the switches

      "Each guest has exactly one switch on." "At each table, the sizes of the guests with switches on must add up to at most the seat count."

    3. 3

      Write the wish as one number to make small

      For example, how unequal the tables are.

    4. 4

      Hand it to a ready-made solver

      Tools such as HiGHS (free), Gurobi and FICO Xpress (paid) use decades of math tricks to find the best switch settings. If they finish, they can prove that nothing better exists.

    The nice design choice: you describe the problem once, in terms of objects, containers, rules and wishes. Then you pick the strategy. Switching from one strategy to the other does not mean rewriting the problem.
    7. Why it is fast

    Only recalculate what changed

    Local search tries a huge number of moves, so each try has to be cheap. The trick is the same one a spreadsheet uses. When you change one cell, the spreadsheet does not recompute every formula. It recomputes only the cells that depend on the one you changed.

    Rebalancer stores the score as a tree of small calculations, called the expression graph. Hosts feed into racks, racks feed into the total score. Pick a move below and see which boxes need new numbers.

    Orange boxes are recalculated. Grey boxes keep their old values. With millions of hosts, the grey part is nearly everything.

    Two more speed-ups from the research paper: many candidate moves are tested at the same time on different processor cores, and the graph stores shared information once instead of once per guest-table pair.

    8. Many wishes

    What if the wishes disagree?

    Say you have two wishes: "tables equally full" and "move few people". Sometimes they pull in opposite directions. Rebalancer gives you two ways to rank them.

    Weights are importance numbers. The solver adds up each wish times its weight and minimizes the total, so wishes trade off. Tiers are strict order. Wish one is fully handled first. Wish two only breaks ties. The code compares tiers like a dictionary sorts words: the first letter decides, and later letters only matter if the first ones match.

    9. Try it

    What the real code looks like

    This is adapted from the Quick Example in the project's README. Four tasks start unevenly on two hosts: three on host0, one on host1. Read the grey comments first.

    # make a solver. The two names only label the logs
solver = ProblemSolver(service_name="rebalancer", service_scope="example")

# the words for "guest" and "table" in this problem
solver.set_object_name("task")
solver.set_container_name("host")

# who sits where right now
solver.set_assignment({"host0": ["task0", "task1", "task2"],
                       "host1": ["task3"]})

# dimensions: each task needs 10 memory, each host has 20
solver.add_object_dimension("memory", {"task0": 10, "task1": 10, "task2": 10, "task3": 10})
solver.add_container_dimension("memory", {}, default_value=20.0)

# a RULE: no host may use more memory than it has
solver.add_constraint(ConstraintSpec(capacitySpec=CapacitySpec(
    name="memory_capacity", scope="host", dimension="memory")))

# the STRATEGY: local search, allowed to move one task or swap two
solver.add_solver(SolverSpec(localSearchSolverSpec=LocalSearchSolverSpec(
    moveTypeList=[MoveTypeSpec(singleMoveTypeSpec=SingleMoveTypeSpec()),
                  MoveTypeSpec(swapMoveTypeSpec=SwapMoveTypeSpec())])))

solution = solver.solve()
print(solution["assignment"])   # a balanced 2-and-2 split

    A good order for exploring on your own:

    1. Install the Python package with pip install rebalancer (Python 3.12 or newer, on Linux or an Apple-silicon Mac). Run the example above.
    2. Read the tutorial in website/docs/getting-started/first-model.md. It builds the same tasks-and-hosts story step by step.
    3. Run the Eight Queens example examples/eightqueens/eightqueens.py twice, once as is and once with --optimal, to see the two strategies disagree.
    4. Open the visual debugger, Rebalancer Explorer. It lets you compare a before and after layout and try "what if I moved this one?". Start it with docker compose up --build and open localhost:3000.
    5. Only then read the C++: solver/solvers/CoreLocalSearchSolve.cpp, then the move types in solver/moves/.
